# Quality, Testing and Release

**Status:** plan, not results. No test described here exists yet except the artefact checks in `tools/` (section 4.11). A box is ticked only with recorded evidence (`VERIFIED_VS_ASSUMED.md`). User-visible behaviour is specified as scenarios in `ACCEPTANCE_TESTS.md`; this document says how the product is tested and released.

## 1. Principles

1. **A feature is not done because the happy path worked once.** It is done when its tests, its failure paths and its documentation exist and pass.
2. **Every claim in the docs, the app and release notes must be backed by evidence** in the ledger. If it is not, it is stated as an assumption or removed.
3. **Failure paths are tested as seriously as success paths**: refused input, lost connections, killed processes, full disks, hostile files.
4. **Never trade correctness for a latency number.** A response is never dropped or falsely acknowledged to meet a performance target.
5. **Tests never touch real data** (section 3).
6. **One definition per fact.** Structures, limits, codes and rules have one canonical home (`SCHEMA_GOVERNANCE.md`); tests are generated from or checked against it.

## 2. Test layers

| Layer | What it covers |
|---|---|
| Unit | Pure logic: validation, scoring, normalisation, PIN generation, step machines, response rules, close policy |
| Integration | Core with real SQLite and real listeners on temporary directories and ports |
| File and crash | Save, lock, recovery, migration, validation of hostile files, interruption at every stage |
| Network | Real WebSocket and HTTP clients, many simulated participants, reconnect and burst behaviour |
| Interface | Automated tests of the Facilitator Workspace, Projector view and Participant page against the screen contracts |
| Real-device | Actual phones on actual access points in real rooms |
| Manual and review | Accessibility, usability, documentation honesty review, packaging |

Each automated test carries its scenario ID in its name (for example `AT-FILE-002`). `tools/check_docs.py` lists scenarios without tests once a stage is finished.

## 3. Environments and isolation

- **Continuous integration builds and runs the tests on Linux and on Windows from Stage 1.** This does not replace hands-on Windows testing (`ROADMAP.md`).
- **Test isolation.** Tests, scripts and tools use temporary directories and ephemeral ports and **never read or write the real application data directory or a real Activity file**. The data directory comes from one resolver; in test mode a missing override makes the application fail to start (`AT-ISO-001`).
- **Fixtures** are generated by the code under test or are checked-in golden files (section 4.4). Tests do not rely on files outside the repository.
- Time-dependent behaviour (grace periods, expiry, rate limits) uses an injectable clock.

## 4. Mandatory automated tests

The scenario IDs show where each requirement is specified.

### 4.1 Listener separation and exposure
`AT-NET-001`, `AT-NET-002`, `AT-PRES-003`, `AT-PRES-005`, `AT-PRES-007`, `AT-PROJ-001`, `AT-PROJ-002`.
- The participant listener's route allowlist is exactly the documented one; **requests to Facilitator or projector paths return 404**, not 401 or 403.
- The projector listener serves only its own routes and only to loopback hosts and origins; wrong `Host` or `Origin` is refused.
- Binding is verified with an operating-system socket listing as well as in-process checks. A bind failure never falls back to a broader binding.
- Projector token: one use; expires; replay refused; after the redirect the address contains no token; logs contain no token.
- The Facilitator webview cannot load remote URLs; only the main window can invoke core commands; the capability allowlist equals the command list in `PROTOCOL_SPEC.md` section 11.
- Join address: the QR content equals `http://<chosen address>:<port>/j/<code>` and never contains `127.0.0.1` or `localhost`.

### 4.2 Submission integrity and protocol conformance
`AT-RESP-001` to `AT-RESP-014`, `AT-JOIN-001` to `AT-JOIN-008`.
- Every row of the **order-of-checks** table and every row of the **duplicate and retry matrix** in `PROTOCOL_SPEC.md` section 5 has a test, including that the idempotency lookup precedes the live, closed and rule checks.
- **Acknowledgement only after commit:** inject a failure between validation and commit and between commit and reply; no false acknowledgement, no duplicate, no loss.
- Response rules, close policy (immediate and grace), re-opening rules, participant limit, zero-response and divide-by-zero cases in aggregates and reports.
- Invalid, oversized and malformed submissions are refused with the right reason code and never stored.
- Every code in the catalogue with `family: protocol` is produced by at least one test with its documented HTTP status.
- **Storage failure** and **suspend/resume and clock jumps** are tested as specified (`AT-RESP-013`, `AT-PRES-011`).

### 4.3 Real-time behaviour
`AT-RECON-001` to `AT-RECON-007`, `AT-PROJ-003`.
- Views apply only if their `rev` is newer; stale and duplicate views are ignored; every close code has the specified client behaviour.
- Reconnect backoff with full jitter (a statistical check that reconnects are spread out); fetch-then-reconnect on page visibility.
- View-build concurrency cap under a mass reconnect while submissions continue; `server_busy` handling.
- A slow client's send queue overflows safely without delaying others; a second connection with the same token closes the first with 4006.
- The reconnect reconciliation table in `PROTOCOL_SPEC.md` section 6 is tested for each row.
- Participant view sizes stay within the cap for every component and step; a larger view fails the build.

### 4.4 Files, migration, locking and crashes
`AT-FILE-*`, `AT-LOCK-*`, `AT-REC-*`, `AT-MIGR-001`, `AT-PERM-*`.
- **Hostile files:** every rule in `reference/validation-rules.md` is triggered by a crafted file and refused with the expected code; the prototype validator in `tools/` already exercises most of them and is replaced by tests against the real implementation.
- **Golden files:** one sample `.actvty` per released format, containing data. Every later version opens each, migrates in the working copy, and the results match expected values. Includes a file with an unknown slide type (read-only; cannot be saved over) and a file with a newer format version (refused).
- **Migrations** run in one transaction; a forced failure leaves the file unchanged; table rebuilds keep columns, indexes, constraints and foreign keys; no data is invented.
- **Save:** a failure injected at each step (including a failed re-validation) leaves the original intact and no stray temporary files; `.bak` written; permissions as specified; save refused if the target changed or the lock is not ours.
- **Crash and interruption:** kill the process mid-save, mid-Live and mid-recovery; recovery offers Recover or Discard, restores committed responses and journaled edits, never claims to restore uncommitted ones, and does not resume Live. Repeat on Linux and Windows. Power-loss behaviour is tested as far as the platform allows and described as tested only to that extent.
- **Locking:** every scenario `AT-LOCK-001` to `AT-LOCK-008`, plus cloud-sync and network location warnings.
- **Safety copies and corruption:** `AT-RESET-001`, `AT-RESET-004`, `AT-RESET-005`, `AT-FILE-014`.
- **Reset and recovery rules:** `AT-RESET-002`, `AT-RESET-003`; Save As, Copy and Template create a new Activity ID with an empty event log and no inherited participant identity (`AT-DATA-005`).
- **Saving for older formats** (from format 2): the compatibility check lists what is lost; the converter output validates against the older version's schemas; chained converters for two versions back (`AT-FILE-015`, `AT-FILE-032`).

### 4.5 Protection
`AT-PROT-001` to `AT-PROT-004`. The tests listed in `SECURITY_FILE_FORMAT.md` section 7: round trip, wrong password and damaged file with the one generic message, corrupted and tampered entries, password confirmation, the no-recovery warning, temporary files removed on every path with no plaintext in them, save keeps protection; on Linux and Windows.

### 4.6 Roster, login and identity
`AT-ROST-*`, `AT-AUTH-*`, `AT-ANON-001`, `AT-IDEN-*`.
- Challenge–response: valid proof accepted; replayed or expired nonce refused; wrong PIN refused; PIN never in any request, log or response.
- **Unknown ID and known ID are indistinguishable** (messages, status codes, timing within a tolerance), including after lockout; lockout counters apply to unknown IDs.
- One active login per ID; device binding; Release; rate limits; length limits.
- Display names: duplicates allowed, disambiguators as specified, name corrections keep identity, roster-mode names cannot be changed by participants, Hide name and Remove participant.
- Participant tokens: only hashes stored; cookie flags; no token in URLs, logs, QR, exports; tokens from one Activity never match another; header fallback works when cookies are blocked.

### 4.7 Exports and escaping
`AT-REPORT-*`, `AT-MOD-003`. Hostile names and answers (formulas beginning with `=`, `+`, `-`, `@`, tab, carriage return; markup and script; very long strings; control characters) in **every** export (CSV, XLSX, HTML) and on every screen. Reports include the provenance block; incomplete results are labelled; denominators are stated; *no answer* and *incorrect* are separate; anonymous slides never show names.

### 4.8 Offline and no external requests
`AT-NET-003`. Load the participant page and the projector page and exercise a full Presentation with the network disconnected; **fail on any request to a host other than the application's own**. Fonts, scripts, images and QR codes are bundled. No requests occur from the Facilitator webview.

### 4.9 Data rules in the product
`AT-DATA-*`, `AT-RESET-*`, `AT-QUIZ-007`. Edit locking after responses exist (cosmetic whitelist only); Live editor read-only; Duplicate and Save a Copy without data; paste between Activities makes a deep copy with new IDs and no responses; edits in one Activity never alter another; undo and redo cover authoring only and never live data.

### 4.10 Errors, logs and diagnostics
`AT-UI-005`, `AT-DIAG-001`. Test values for tokens, PINs, passwords, names and response text never appear in logs, error details or diagnostic reports; access logs omit query strings; error codes are stable and every code has a message key.

### 4.11 Contract and artefact drift (CI)
Run on every change, and today as scripts:
- `tools/validate_artefacts.py` (schemas valid, registries valid and consistent, `x-limit` equals the registry, examples behave, migration applies, golden file passes, each file rule fires on a crafted file).
- `tools/gen_reference.py --check` (generated reference tables are current).
- `tools/check_docs.py` (cross-references, identifiers, terms, scenario coverage in both directions).
- Once code exists: the Rust types and TypeScript types are generated from, or proven equal to, the schemas; the migration set applied to an empty database equals the committed schema snapshot; every example and golden file validates with the product's own validator.

### 4.12 Interface tests
`AT-UI-*`. Automated checks of the screen contracts: disabled controls expose their reasons; Enter never confirms a destructive action; keyboard-only workflows; validation messages and focus; the live region for counters; touch target sizes on the Participant page; presence of the Active count and join area on every projector screen.

## 5. Behavioural lessons re-created as scenarios

These behaviours were learned from an earlier prototype of a similar application. They are re-created as new tests for this stack; **no prototype code is reused**:

| Behaviour | Scenario |
|---|---|
| A vote submitted twice (retry) is stored once | `AT-RESP-002` |
| A lost acknowledgement does not lose or duplicate the vote after reconnect | `AT-RECON-002` |
| A page refresh keeps the participant's identity and recorded answer | `AT-RECON-005` |
| A reconnecting client resynchronises to the current step | `AT-RECON-004` |
| Submissions after close are refused and change nothing | `AT-RESP-005` |
| An application restart keeps all committed data | `AT-REC-001` |
| Results with zero responses show zeros, not errors | `AT-PREV-001`, `AT-CNT-001` |
| An invalid join code and an invalid option give clear, safe errors | `AT-JOIN-002`, `AT-RESP-008` |

| The displayed join address is correct for phones (never loopback) | `AT-PRES-005` |

## 6. Capacity and performance validation protocol

**Purpose:** to decide what the product may truthfully claim. Nothing is claimed beyond what passes.

**Record for every run:** date; application version; Facilitator computer (model, CPU, memory, operating system and version); access point or router model, firmware, band, channel and settings (including client isolation off); network topology (wired or wireless Facilitator laptop); load generator and where it ran; number of simulated and real devices; scenario; start and end times; results as below; notes on interference or anomalies.

**Scenarios** (at 30, 100 and 200 participants, as far as the hardware allows):
- **Join burst:** all participants join within a few seconds.
- **Answer burst:** all answer within about two seconds of a step opening.
- **Result updates:** projector and phones while answers arrive.
- **Reconnect storm:** the access point drops and returns; all phones reconnect.
- **Long run:** at least 60 minutes of mixed activity.
- **Slow and misbehaving clients:** some clients stall, send oversized input, or retry aggressively.
- Each Slide Type available at the time.

**Measure:** submit-to-acknowledgement latency (median, 95th and 99th percentile); failures; **duplicates (must be zero)**; lost acknowledgements; refusals by reason; application CPU and memory; database commit timings; send-queue overflows; view build time and size against the budget; time to full recovery after the reconnect storm.

**Rules:**
- Repeat each scenario at least three times; report the range.
- A simulator on the same computer over loopback does not test Wi-Fi. Network claims need load generated from **separate devices over the real access point**, with some **real phones** in the mix.
- Never raise throughput by dropping, delaying silently, or acknowledging before commit.
- Results are stored in the repository with the raw data and linked from the ledger. Release notes and the participant limit default quote only measured envelopes, for example "validated at N participants on this hardware and access point".

## 7. Real-device and venue trials

- At least two different venues or network setups, including one with the Facilitator on a hotspot or travel router, and one where the Facilitator is not close to the access point.
- Several phone models and both Android and iOS browsers, including older devices within the supported range.
- Scan the QR code from the back of the room; lock and unlock phones; toggle Wi-Fi; restart the application; kill and relaunch during Live and recover.
- Informal pilots with a small real group at the end of Stage 2 and Stage 4; record what confused people and what failed.
- Record what failed, as well as what worked, in the ledger.

## 8. Accessibility and internationalisation checks

- **Accessibility target:** WCAG 2.2 AA. Checks: keyboard-only operation of the entire Facilitator Workspace; visible focus; screen-reader testing on at least one Windows and one Linux screen reader for the Facilitator Workspace and a phone screen reader for the Participant page; contrast measurement of every theme; 200% zoom; reduced motion; target sizes; non-drag alternatives; status announcements; correct/incorrect not by colour alone.
- Results are recorded; **no conformance is claimed** until the checks are documented, and then only for what was checked.
- **Internationalisation:** all interface text comes from language resource files (a lint rule or review checklist rejects hard-coded interface strings). Bidirectional and special-text cases are tested on every screen that shows user text: very long names without spaces, emoji, combining marks, mixed Arabic and Latin, right-to-left only text, text with control characters. Word Cloud and leaderboard layout are checked with such text.
- Fonts: bundled; the choice for non-Latin scripts is an open decision with a licence check.

## 9. Governance, dependencies and naming

- **Neutral internal name.** Code, package names, protocol identifiers, the file format `format` value, cookie names and test fixtures use a neutral internal name, not a candidate product name. The user-visible product name lives in **one constant** (and the language resource files), so a name change touches one place. The `.actvty` extension is independent of any brand; it has not been checked for conflicts with other software.
- **No product name is selected.** Before any public use, a name screening is done (existing products, trademarks in intended markets, domain names, open-source and package-manager names, app store names).
- **Dependencies.** A licence inventory is generated and checked from Stage 1 (Rust crates, npm packages, bundled fonts, icons, images, SQLite build); incompatible or unclear licences block inclusion. Lock files are committed and dependencies pinned. Vulnerability checks run in CI; a finding is fixed or recorded with a reason. Every new dependency needs a licence check and a maintenance check (activity, ownership, size, necessity).
- **Product licence and distribution terms** (open source, proprietary, freemium terms) are an open decision to be made before the first public release.
- **Third-party assets.** No assets, layouts or text are copied from other products. Fonts are used only under licences that permit bundling.
- A `THIRD_PARTY_LICENSES` file ships with every release.

## 10. Release checklist

A release is allowed only when **every** item is ticked with evidence, or the corresponding claim is removed from the release notes and docs.

1. All automated tests pass on Linux and Windows CI.
2. Listener separation and exposure tests pass (section 4.1).
3. Submission integrity, protocol conformance and real-time tests pass (4.2, 4.3).
4. File, migration, locking and crash tests pass, including golden files from every released version (4.4).
5. Protection tests pass, if protection is included (4.5).
6. Roster, login and identity tests pass (4.6).
7. Export and escaping tests pass (4.7).
8. The offline test passes with no external requests (4.8).
9. Capacity validated and recorded, **or** the release states "capacity not validated" and keeps the default participant limit (section 6).
10. Real-device trials done and recorded (section 7).
11. Hands-on testing done on each operating system for which support is claimed; **Windows is not claimed unless tested on a Windows machine**.
12. Accessibility checks done and recorded, **or** no accessibility conformance is claimed (section 8).
13. Packaging tested: install, launch, file association, upgrade, uninstall, on each supported operating system.
14. Licence inventory complete; vulnerability checks clean or accepted with reasons; `THIRD_PARTY_LICENSES` generated.
15. Redaction tests pass (4.10); a manual search of a full-run log finds no secrets.
16. **Every Must scenario in `ACCEPTANCE_TESTS.md` for the stages included has an automated test or a dated manual run record; contract and artefact drift checks pass (4.11).**
17. Documentation honesty review: every claim traced to the ledger; Known limitations present and current; the manual topics listed in `NETWORKING_AND_DEPLOYMENT.md` section 13 exist.
18. The ledger (`VERIFIED_VS_ASSUMED.md`) is current; no release-note claim rests on an item still marked assumed.
19. Decision register current; no open blocker in `READINESS_AUDIT.md`.

## 11. Defects and evidence

- Defects affecting data integrity, security separation, acknowledgement correctness or honesty of reports are release blockers regardless of how rare they are.
- Each fix adds a test that fails without the fix, and cites the scenario ID it protects (adding one if none exists).
- Evidence (logs, measurements, screenshots) is kept with the commit or issue that produced it and linked from the ledger.
