# Glossary

One set of terms is used in the app, the docs and the manual. If a term is not here, add it here before using it anywhere else. The word *session* is deliberately **not** a product term (the product has no per-presentation history records); use **Live**, **Presentation** or **participant token** instead.

## Documents and structure

| Term | Meaning |
|---|---|
| **Activity** | The document. One `.actvty` file holding slides, theme, settings, optional roster, stored responses and a small event log. Each Activity has an **Activity ID** created with it; Save As, Save a Copy and Save as Template create a new one. |
| **Slide** | One item in the sidebar of the Facilitator Workspace. Every slide has a Slide Type. This is the word users see. |
| **Slide Type** | The kind of slide: Multiple Choice Poll, Quiz Question, Leaderboard, Content, Open Question, Word Cloud, Q&A. |
| **Step** | One screen a slide moves through while presented (a Quiz Question has Question, Reveal, Stats). A slide has one or more steps. |
| **Component** | The technical module in the code that implements one Slide Type. Not a user-facing word. |
| **Slide envelope** | The generic wrapper of every slide file (ID, type, type version, settings, notes) around type-specific content. |
| **Theme** | Colours and fonts, set once per Activity. |
| **Template** | A copy of an Activity with no responses and, optionally, no roster. Made with *Save as Template* or *Save a Copy Without Responses*. |
| **Quiz settings** | Activity-wide scoring and feedback settings that apply to every Quiz Question in the Activity. |

## People and surfaces

| Term | Meaning |
|---|---|
| **Facilitator** | The person running the Activity (also called presenter, trainer or teacher elsewhere; the docs use Facilitator). |
| **Participant** | Anyone who joins from a phone, tablet or laptop and responds. |
| **Facilitator Workspace** | The desktop window where the Facilitator authors, previews and controls. Holds one tab per open Activity. |
| **Projector view** | A display-only web page opened in a browser window on the Facilitator's computer, normally full screen on the second screen. |
| **Participant page** | The lightweight web page participants open on their own devices. |
| **Screen card** | One entry in `SCREEN_SPEC.md` describing a screen's contract. |
| **Sketch** | A low-fidelity layout drawing in `sketches/`. Not a visual design. |

## Running an Activity

| Term | Meaning |
|---|---|
| **Preview** | Trying a slide inside the Facilitator Workspace against a throwaway data store. Nothing is kept. No network server is needed. |
| **Present** | Running slides for real. The participant server is on and responses are stored. |
| **Live** | The runtime state of an Activity while it is being presented. At most one Activity is Live in an application instance. |
| **Idle** | The runtime state when an Activity is not being presented. |
| **Presentation** | One Live period, from *Start presenting* to *End presenting*. Recorded in the event log. Presentations are **not** stored as separate datasets. |
| **Recovered** | The state after an unexpected exit, when the app finds a leftover working directory and offers Recover or Discard. |
| **Join address** | The complete URL participants open, for example `http://192.168.1.23:47831/j/K7M2`. |
| **Join code** | The short code at the end of the join address (`K7M2`). Never shown alone. |
| **QR code** | Encodes exactly the join address. |
| **Lobby** | The first projector screen when going Live: join address, QR code, and who has joined. |
| **Participant limit** | The maximum number of participants admitted in one Presentation, set in the *Start presenting* dialog and enforced by the server. |

## Data and counters

| Term | Meaning |
|---|---|
| **Response** | One accepted submission by one participant to one slide. |
| **Submission** | What a phone sends. Carries a **submission ID**. It becomes a Response only after being accepted and durably stored. |
| **Submission ID** | A random value generated by the phone per submission, used to recognise retries. |
| **Acknowledgement** | The server's reply that a submission was durably stored. Sent only after commit. |
| **Outcome** | The result of a submission: `accepted`, `duplicate` (the original accepted outcome replayed) or `refused` (with a reason code). |
| **Stored responses** | Responses saved for a slide, including those from earlier Presentations. |
| **Active participants** | Participants connected right now (connection alive and answering pings). Shown on every slide. |
| **Answered** | Among active participants, how many have a response stored for this slide. |
| **Accepting responses** | A switch on a slide while Live. Off turns the slide into a results display. |
| **Close policy** | How a slide stops accepting responses: **Immediate**, or **Grace period** (a few seconds during which in-flight answers are still accepted). |
| **Closed** | A slide that has stopped accepting responses through its close policy. |
| **Incomplete result** | Results from a slide that was still open when the Presentation ended or was interrupted. Labelled as such in every report. |
| **No answer** | A participant who was active while a slide was open but submitted nothing. Reported separately from **Incorrect**. |
| **Reset** | Deleting stored responses for one slide, or stored responses and stored participant records for the whole Activity. Slide content and roster are kept. |
| **Safety copy** | An automatic full copy of the working state made just before a Reset. |
| **Response rule** | How a slide treats repeat answers: one per participant (default), replace until closed, or multiple. |
| **Cosmetic change** | A change that cannot alter what responses mean (theme, speaker notes, slide order, participant visibility). The only edits allowed once a slide has stored responses. |
| **Slide status** | **Incomplete** (mandatory fields missing) or **Ready**. Not to be confused with *Incomplete result*. |
| **Event log** | A small list inside the Activity of Presentations, Resets, interruptions and similar events. Contains no names, responses or tokens. |
| **Revision (`rev`)** | A counter that increases whenever the Presentation state changes; a client applies a view only if its `rev` is newer than the one it holds. |
| **View** | The complete current screen state sent to one audience (a participant page or the Projector view) in one message. |

## Identity

| Term | Meaning |
|---|---|
| **Join mode** | How participants identify themselves: **Anonymous**, **Display name**, or **Roster login**. Chosen when starting to present. |
| **Response mode** | Per slide: **Anonymous** (answers are not linked to names in the app or reports) or **Identified** (answers are linked to the participant). |
| **Display name** | A label a participant types. Duplicates are allowed. Never an identity. |
| **Disambiguator** | A small number shown beside a display name when two identical names appear together. |
| **Roster** | The list of expected participants stored in the Activity (`roster.json`). |
| **Participant ID** | The `user_id` column of the roster. |
| **PIN** | The secret a roster participant types to log in. Not called "password". |
| **Participant token** | A random value kept in the participant's browser so that reconnecting resumes the same identity. |

## Files, versions and safety

| Term | Meaning |
|---|---|
| **Working directory** | A private temporary folder where an open Activity is unpacked and where its live database sits. |
| **Lock file** | `<name>.actvty.lock` beside the file; marks that it is open for editing in an application instance. Cooperative only. |
| **Read-only view** | Opening a locked file without taking the lock. Cannot be saved over the original. |
| **Independent copy** | A new file made from a read-only view or by Save As. Has its own lock and never overwrites the original. |
| **Protected** | An Activity file whose entries are encrypted with a password (optional). |
| **.bak file** | The previous saved version, kept as one generation beside the file. |
| **Format version** | The integer `format_version` in the manifest: the compatibility gate. Independent of the application version. |
| **Data schema version** | The number of the latest applied database migration (`user_version`). |
| **Type version** | The integer version of one Slide Type's schema. |
| **Compatibility check** | The list shown before saving a copy in an older format, naming what will be lost or simplified. |
| **Canonical artefact** | A machine-readable definition that is the single source of truth for a structure: a JSON Schema, a numbered SQL migration, the limits registry, the error-code catalogue or the validation-rule catalogue. |
| **Limits registry** | `schema/limits.json`: every numeric limit, with an ID, in one place. |
| **Validation rule** | A numbered check (`VAL-...`) applied to a file before it is opened. |

## Documentation terms

| Term | Meaning |
|---|---|
| **Verified** | Checked by a test, measurement or a dated external source, and recorded in `VERIFIED_VS_ASSUMED.md`. |
| **Assumed** | Believed but not yet checked. Must be labelled as such wherever it matters. |
| **Confirmed / Proposed / Open** | Decision statuses in `DECISIONS.md` (`D-nnn`, `PR-nnn`, `O-nnn`). |
| **Acceptance scenario** | A numbered Given/When/Then scenario (`AT-...`) in `ACCEPTANCE_TESTS.md`. |
| **Must / Should / Could** | Scenario priority. Only *Must* scenarios block a release. |
